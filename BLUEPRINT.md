# Sonder — Functional Blueprint

> Generated by exhaustive repository exploration. Documents **behavior and function only** — no colors, fonts, spacing, layout grids, or visual styling. A rebuild team should be able to reproduce every screen's logic, data, and navigation from this document alone, using any visual design.

---

## 1. Overview

**Sonder** is an interactive proof-of-concept (PoC) for an adaptive, misconception-based diagnostic system for secondary-school Mathematics, Physics, and Chemistry. Instead of grading a student right/wrong on a quiz, the product's premise is that it identifies the *specific wrong mental model* (a "misconception") behind a student's incorrect answers, by adaptively choosing follow-up questions and tracking a probability distribution over a small set of candidate misconceptions ("hypotheses") until one is confidently confirmed, or the system gives up and asks a human teacher for judgment.

This build is **entirely a front-end scripted demo**: there is no real backend, no real database, no real authentication, and no real AI/ML — every "diagnosis," "generated question," "AI consultant reply," and "search result" is a pre-written value in a static fixture file, played back step-by-step through simple pointer-advancing UI logic. This is stated directly in the product's own landing copy: *"This build runs on scripted data,"* *"No real backend, auth or AI. Data is fixture-scripted."*

**Who uses it (four roles, chosen — not logged into — from a single landing screen):**
- **Student** — takes a diagnostic, reads a study note once diagnosed, checks a past fix has held, browses a reference "Learn" library, and asks a scripted AI consultant about their own history.
- **Teacher** — is the human gate: every diagnosis or AI-generated question must pass a teacher's review before it can reach a student or parent. Teachers replay session evidence, approve/correct/reject diagnoses, resolve escalations, vet AI-generated question batches, and consult their own scripted AI assistant.
- **Parent** — sees only teacher-approved, plain-language summaries of their child's diagnoses — never raw scores, probabilities, or evidence.
- **Admin** (content & curriculum lead) — curates and audits the system at a level above any one student: the full misconception catalogue, coverage gaps in the question bank, aggregate accuracy/performance metrics versus simpler baseline methods, and a provenance/audit log of every AI-generated artifact.

**Main areas of the site:**
- Landing / role picker (`/`)
- Student workspace (`/student/**`)
- Teacher workspace (`/teacher/**`)
- Parent workspace (`/parent/**`)
- Admin workspace (`/admin/**`)
- A developer-only shared-component gallery (`/dev/components`), not part of the end-user product
- A custom 404 ("not found") page

### Authentication flows

There is **no real authentication** of any kind — no password, no signup form, no email verification, no session token, no server-side check.

- **"Sign in"** = visiting the landing page (`/`) and clicking one of four role cards (Student / Teacher / Parent / Admin). Clicking a card immediately stores the chosen role string in the browser's `localStorage` (key `sonder.role`) and navigates to that role's home route.
- **Session persistence**: because the role is read from `localStorage`, refreshing the page or closing and reopening the browser keeps the same role signed in (no session expiry, no timeout).
- **Switching roles**: a role-switcher menu (in the persistent top header, present on every non-landing page) lets the user instantly become any of the other three roles from anywhere in the app — this immediately updates `localStorage` and, if the current page isn't a valid destination for the new role's area, effectively re-homes on the next navigation (the visible page keeps rendering; the shell's sidebar/data context updates).
- **Sign out**: the same role-switcher menu has a "Sign out" item — clears the stored role from `localStorage` and navigates back to `/`.
- **Deep-linking while signed in as a different role**: if a user is signed in as (say) Teacher and manually navigates to a Student-area URL, the Student area's guard silently switches the stored role to Student (no confirmation prompt, no error) rather than blocking access. Content on the page always renders; this correction only ever affects which role is *recorded* as current.
- **Visiting a role's URL while fully signed out**: the guard on that area detects there is no stored role and redirects (client-side) back to `/`.
- **No password reset, no email verification, no "forgot password" flow** — these concepts don't exist in this build; there is no email address ever collected or referenced for any role.
- **Server vs. client rendering of auth state**: because the "session" only exists in browser `localStorage`, the server always initially renders as if signed out; the real role is known only after the page hydrates in the browser. This means there is a brief moment on first load where role-dependent UI (e.g., the sidebar, the not-found page's "back to home" link) doesn't yet know the role.

### Persistent navigation (present on every route except `/` and `/dev/*`)

A shared application shell wraps every role-area page:
- **A collapsible side navigation panel**, whose contents are entirely role-dependent (see per-role groupings below). Its collapsed/expanded state is remembered per-browser (persisted locally) independent of role or page. On small screens the sidebar instead becomes an off-canvas drawer opened via a menu button and closed by tapping outside it or an explicit close control.
- **A top bar** containing:
  - A breadcrumb trail derived automatically from the current URL path — every segment except the last is a clickable link to that ancestor path; segment labels are human-readable overrides (e.g. the path segment `content-review` displays as "Content review", `review` displays as "Two-reviewer check") where a mapping exists, else the raw segment is capitalized.
  - A light/dark appearance toggle (a pure display preference, not covered further per the "no visual design" rule beyond noting it exists and is available everywhere).
  - A **role menu**: shows the current persona's name; opens to reveal the full persona/context strip, a "Switch workspace" list of all four roles (clicking one instantly re-signs-in as that role and navigates to its home), and "Sign out".
- Route transitions render inside this shell without a full page reload.

**Per-role sidebar contents:**
- **Student:** Home · New diagnostic · Learn — then, under an unlabeled "Progress" grouping: My insights · Ask the consultant.
- **Teacher:** Dashboard — then under "Queues": Escalations · Content review — then under "Assist": AI consultant.
- **Parent:** Summaries (the only item).
- **Admin:** Overview — then under "Content": Catalogue · Coverage · Provenance — then under "Insight": Performance.

**Conditional navigation:** the sidebar's entire content set switches based on the current role; there are no items visible to some users within a role but not others (no sub-role permission tiers). A few in-page destinations are reachable only by drilling in from another screen and are never listed in the sidebar at all: the diagnostic session screen, the verification/remediation screens, the Learn concept pages, the teacher's per-scenario evidence/review screens, the content-review agreement and generation-run detail screens, and the teacher's per-student insights screen.

## 4. Screen-by-Screen Breakdown

### 4.0 Global / Cross-Role Screens

#### Landing / role picker — route: /

**Purpose:** Single entry point for the whole application; establishes which of the four roles the visitor is acting as (this build's substitute for login).

**Entry points:** First visit to the site; after "Sign out" from any role.

**Elements & behavior:**
- A one-line product identity mark and name.
- A headline and one paragraph describing the product ("One engine across Maths, Physics and Chemistry. Every result passes a teacher before a student or parent sees it. This build runs on scripted data — choose a workspace to sign in.").
- Four role cards, one each for Student, Teacher, Parent, Admin, in that fixed order, each showing: the role's label, the demo persona's name and one-line context (e.g. "Grade 9 · [school]"), and a one-sentence description of what that role does in this build. Clicking any card immediately signs in as that role (writes it to local storage) and navigates to that role's home route. No card is ever disabled.
- A small footer row: a link to the developer component gallery (`/dev/components`), and a disclosure line: "No real backend, auth or AI. Data is fixture-scripted."

**Data displayed:** The four roles' static metadata (label, persona name, context line, description) — not derived from any per-user data, since there is no per-user data yet at this point.

**Forms:** None (pure click-to-choose, no fields).

**States:** No loading/empty/error states — fully static.

**Exit points:** Any of the four role homes (`/student`, `/teacher`, `/parent`, `/admin`); the component gallery.

**Conditional behavior:** None — identical for every visitor regardless of any prior session (choosing a role always simply overwrites whatever was previously stored).

#### Not found (404) — route: *(any unmatched path)*

**Purpose:** Replaces the framework's bare default error page with one that stays inside the app's shell and always offers a way back, for a mistyped, stale, or never-built URL.

**Entry points:** Navigating to any URL that doesn't match a real route (including malformed dynamic-segment values that a page explicitly rejects, e.g. an unknown scenario id).

**Forms:** None.

**States:** This page *is* the error state for the whole site's routing — there's no further loading/empty state within it.

**Exit points:** The signed-in role's home, or the landing page.

**Conditional behavior:** The single conditional is described above (button destination/label depends on whether a role is currently signed in).

### 4.1 Student Area

All student routes are wrapped by a guard that redirects a signed-out visitor to `/` and silently adopts the Student role for a visitor deep-linked here while signed in as someone else. The signed-in student identity throughout this area is the single fixed demo persona ("Zara Qureshi"); there is no multi-student switcher within the Student role.

#### Student home — route: /student

**Purpose:** Landing dashboard for the signed-in student; surfaces anything currently actionable and the three main jumping-off points into the area.

**Entry points:** Student role's default home; sidebar "Home"; role-switch to Student from any other role.

**Elements & behavior:**
- A personalized greeting using the student's first name, with a "New diagnostic" primary action.
- A **"Follow-up check due"** card — always shown, always pointing at the same specific scripted scenario regardless of the student's actual state — linking to the verification-check screen.
- A **"Last session"** card — always shown, always referencing the same scripted scenario, displaying a "diagnosed" status badge and "study note ready to read" — linking to the remediation screen.
- A "Where to go next" section with three navigation cards: New diagnostic, My learning-pace insights, Ask the AI consultant.

**Data displayed:** The signed-in persona's name (for the greeting). The two shortcut cards' copy is fixed text, not computed from any per-session data store — see Business Rules and Open Questions.

**Forms:** None.

**States:** No loading/empty/error states — identical every visit.

**Exit points:** New-diagnostic picker, follow-up check, remediation/study-note screen, insights, consultant.

**Conditional behavior:** None — this screen never varies with the student's actual diagnostic history in this build.

#### Start a diagnostic — route: /student/start

**Purpose:** Two-step picker — choose a subject, then either a specific topic or a whole-subject "broad check" — that launches a scripted diagnostic session.

**Entry points:** Home page's "New diagnostic" action/card; sidebar "New diagnostic".

**Elements & behavior:**
- **Step 1 — Subject:** one card per subject (Mathematics, Physics, Chemistry), each showing its name and a topic count. Clicking a card selects it and advances to Step 2. No subject is ever disabled.
- **Step 2 — Topic** (shown once a subject is chosen): a "Change subject" control returns to Step 1.
  - A **"Broad check across all of {subject}"** action — always enabled — launches that subject's whole-subject scripted scenario in "general" mode.
  - A list of the subject's topics, each showing its name and a one-line description. A topic is clickable (launches its scripted scenario in "topic" mode) only if a scenario has actually been authored for it; otherwise it is visibly disabled and labeled "Not in this build."

**Data displayed:** The subject/topic taxonomy (three subjects; each subject has several topics, only one of which is fully wired to a scripted scenario in the current build; the rest are stubs).

**Forms:** None (click-to-navigate only, no text entry).

**States:** No loading/empty/error states — the taxonomy is fixed and always populated.

**Exit points:** The diagnostic session screen (in "general" or "topic" mode, depending on the entry chosen), or back to Step 1.

**Conditional behavior:** Whether a topic is clickable depends entirely on whether that topic has a scripted scenario wired to it. As built, exactly one topic per subject is wired: Mathematics → "Rounding to decimal places"; Physics → "Kinetic energy and work"; Chemistry → "Moles and stoichiometry." All other topics (fractions, negatives, indices, forces, waves, bonding, acids) are unwired stubs.

#### Diagnostic session — route: /student/session/[scenario]/[mode]

**Purpose:** The core scripted diagnostic experience: the student answers a sequence of pre-scripted multiple-choice questions one at a time; the session ends in either a confirmed diagnosis or an "unsure — handed to your teacher" outcome, both entirely pre-authored per scenario rather than computed live from the student's actual choices.

**Entry points:** The Start-a-diagnostic picker (both the "broad check" and per-topic launches); a "Run again" control on this screen's own end state (restarts the same scenario/mode from the beginning).

**Elements & behavior, by phase:**
- **Intro:** states the mode ("Broad subject check" or "Topic diagnostic"), the subject or topic name, and that the student will get one question at a time up to a stated maximum, with no time limit and no visible score. A "Begin" action starts the questioning.
- **Question:** shows a running "Question N of up to {maximum}" counter and a progress indicator, the current question's text, and one button per answer option (lettered A, B, C…). Clicking an option briefly shows it as selected during a short simulated "thinking" pause, then advances to the next pre-scripted step (or to the end state, if that was the last question). A persistent footer note tells the student that the system's reasoning is never shown to them — only to their teacher.
- **Thinking (brief, automatic):** a short simulated processing pause between a click and the next question appearing — purely a pacing device; nothing is actually computed during it, since the next step already exists in full.
- **Done:** shows the scenario's final headline and outcome message inside a large diagnosed/unsure status indicator.
  - If **diagnosed**: a "See your study note" action leads to the remediation screen for this scenario.
  - If **unsure**: a "Back to home" action, plus a secondary "Learn about a related concept" link to the Learn hub, and a note that nothing is shared with the parent until a teacher has reviewed it.
  - A "Run again" control is always present and fully replays the same scenario/mode from the start.

**Data displayed:** The scripted scenario's subject/topic labels, its maximum-question count, each step's question text and answer options, and the final outcome type/headline/message. The system deliberately never displays: the probability distribution over candidate misconceptions, the system's stated reasoning for each question, the "correct" answer, or the specific option the fixture recorded as "given" (which, notably, is fixed per scenario step regardless of which option the student actually clicks — see Business Rules).

**Forms:** No text entry — pure single-choice button clicks, one attempt per question, no retry/undo on an individual question.

**States:** No loading/error state beyond the brief simulated pause. Visiting with an unrecognized scenario or mode value produces the site's standard not-found (404) page before any session content ever renders.

**Exit points:** The remediation/study-note screen (diagnosed outcome), the student home (unsure outcome), the Learn hub (unsure outcome, secondary link), or a full in-place restart.

**Conditional behavior:** The `mode` segment (topic vs. general/broad) only changes the introductory and header wording — the same underlying question sequence plays either way for a given scenario. The diagnosed-vs-unsure branching, and everything about the questions asked, is fixed per scenario at authoring time; it is not actually derived from which options the student clicks during play.

#### Follow-up verification check — route: /student/verify/[scenario]

**Purpose:** A single fresh question, presented as happening some time after a diagnosis was resolved, to check whether the earlier fix has genuinely held — a real (if minimal) input-driven check, unlike the main diagnostic session.

**Entry points:** The home screen's "Follow-up check due" card; a "Preview the follow-up check" option on the remediation screen, when available for that scenario.

**Elements & behavior:**
- A short context sentence framing this as a delayed spot-check, not a new topic.
- **Unanswered state:** the check's question text and one button per answer option. Clicking an option genuinely determines the outcome (unlike the main session).
- **Answered state:** compares the chosen option to the check's correct answer:
  - Match → a positive banner: "The fix held," with a note that there's nothing more to do on this misconception for now.
  - Mismatch → a warning banner: "This one slipped back," with a note that the teacher has been notified and will revisit it. (This message describes a notification side effect that isn't actually implemented in this build — no teacher-facing state changes as a result.)
- A single "Back to home" action.

**Data displayed:** The scripted verification check tied to this scenario (a context line, question, options, and the correct answer).

**Forms:** A single-select multiple-choice question; one attempt only — there's no "change my answer" control once a choice is made.

**States:** No loading/error state. Two outcome states (held / slipped) plus the initial unanswered state. Visiting for a scenario with no scripted verification check (or an invalid scenario id) produces the standard not-found page.

**Exit points:** Student home only.

**Conditional behavior:** Whether the "held" or "slipped" banner shows depends purely on whether the chosen option's text exactly matches the scripted correct answer — any other wrong option produces the same "slipped back" message (the fixture data distinguishes a specific "relapse" answer from other wrong answers, but this distinction is not currently used by the screen's logic).

#### Study note / remediation — route: /student/remediation/[scenario]

**Purpose:** The plain-language explanation and correction handed to the student once a diagnosis is complete — the payoff screen for a "diagnosed" session outcome.

**Entry points:** The diagnostic session's "See your study note" action (diagnosed outcome only); the home screen's "Last session" card.

**Elements & behavior:**
- A note that this was "shared with you after your teacher reviewed the diagnosis" (framing only — this build doesn't technically gate the page on an actual teacher decision; it is simply shown whenever the route is reached).
- "What was going on" — a plain-language description of the specific misconception.
- "How to think about it" — the corrective explanation, including a worked re-do of an example.
- A video reference (an external link opening in a new tab).
- A **"Mark as read"** action: shows a confirmation message (which claims the note "can be found again from My insights") and returns to the home screen. This does not actually persist any read/unread state anywhere, and no such list exists on the Insights screen — the confirmation's claim doesn't correspond to any real stored effect.
- A **"Preview the follow-up check"** action, shown only if a verification check has been scripted for this scenario.
- A **"Learn more about this"** action, shown only if a full Learn concept page exists for this misconception.

**Data displayed:** The scripted study note's title, explanation, correction, and video reference.

**Forms:** None (action buttons only).

**States:** No loading/empty/error state; the two conditional action buttons simply don't render if their underlying content doesn't exist. Visiting for a scenario with no study note (i.e., one that never reached a diagnosed outcome) produces the standard not-found page.

**Exit points:** Student home (via Mark as read), the verification check (if available), the matching Learn concept page (if available), the external video link (new tab).

**Conditional behavior:** The two optional action buttons appear independently depending on whether a verification check and/or a matching Learn page exist for this specific scenario.

#### Learn hub — route: /student/learn

**Purpose:** A browsable reference library of every known misconception across all three subjects, independent of ever having been diagnosed with any of them — always available to consult.

**Entry points:** Sidebar "Learn"; the "unsure" session outcome's secondary link; occasionally reached in the reverse direction from the remediation screen (which links to a specific concept page, not this hub, when one exists).

**Elements & behavior:**
- Grouped by subject (Mathematics, Physics, Chemistry, in that order — a subject with no entries is simply omitted).
- One card per known misconception, showing its short code, name, and description, plus a trailing state:
  - **"Open"** — present only if a full concept page has been authored for that misconception; leads to the concept page.
  - **"Notes coming soon"** — a non-interactive label, shown for every catalogued misconception without an authored page yet.

**Data displayed:** The complete misconception catalogue across all subjects — every entry is listed regardless of its validation status (validated, pending, or "catalogued only" all appear identically here; only page availability changes the card's trailing state).

**Forms:** None (browse-only).

**States:** No loading/error state. A subject section with zero entries would be omitted entirely (not currently reachable, since every subject has at least one entry).

**Exit points:** Any concept page that has been built.

**Conditional behavior:** Only a small minority of catalogued misconceptions currently have a built concept page (one per subject, matching the same three wired scenarios): Mathematics' rounding-digit error, Physics' linear-in-speed kinetic-energy error, and Chemistry's coefficient-ignoring mole-ratio error. All others show "Notes coming soon."

#### Concept page — route: /student/learn/[subject]/[code]

**Purpose:** A full, self-contained explainer for one specific misconception — notes, a worked example, a simulated "search results" list of further resources, and a concept-scoped scripted chat — reachable independent of ever having been diagnosed with it.

**Entry points:** The "Open" action on the Learn hub; the "Learn more about this" action on a matching remediation screen.

**Elements & behavior:**
- Notes section: "What this is," "How to think about it," and a worked example (a prompt, the typical wrong move, the fix, and the final answer).
- **Recommended resources section:** on first view, shows a brief "searching the web" placeholder for well under a second, then reveals a fixed, pre-ranked list of external resource links (video/article/interactive), each showing a title, a relevance score, a source, and a one-line rationale for why it was picked — explicitly labeled as a scripted result, not a live search. There is no user-facing search box, filter, or sort control here; "searching" is a simulated pause before revealing an already-fixed, already-ordered list.
- **"Ask about this concept" chat:** a scripted chat scoped specifically to this one concept (distinct from the general AI consultant, which is scoped to session history):
  - Opens with a greeting message.
  - Two chips that are always available regardless of conversation progress: "Explain it simpler" and "Give me a harder example."
  - Additional suggested-question chips, each of which disappears once asked (via chip or by typing matching text).
  - A free-text input that matches typed questions against the same scripted set (exact match, case-insensitive) or otherwise returns a generic fallback reply.
  - Every reply is preceded by a brief simulated "typing" delay.
  - Some replies include an inline worked example, and/or "Next: {topic}" follow-up buttons that surface additional related scripted answers.
  - Footer shortcuts jump back to the notes or resources sections on the same page.

**Data displayed:** The concept's title, explanation text, worked example, list of scripted resources (title/source/kind/relevance/rationale/link), and its dedicated chat script (greeting, question/answer entries, fallback).

**Forms:** The chat's free-text input (no formal validation beyond "not empty, not currently waiting on a reply").

**States:** The resource list has a brief "searching" state before always settling into its fixed "done" state (no error state — the timer always resolves the same way). The chat has message-list and pending-reply states, no error state.

**Exit points:** External resource links (new tab); same-page anchor jumps. No route-to-route navigation from within the page besides the persistent global navigation.

**Conditional behavior:** Content is entirely specific to which of the (currently three) built concept pages is being viewed — each has its own notes, three resources, and a four-entry chat script.

#### My learning-pace insights — route: /student/insights

**Purpose:** The student's own view of how quickly their diagnosed misconceptions get resolved compared to a class-wide median, plus one synthesized suggestion for what to focus on next — explicitly framed as "not a grade."

**Entry points:** Sidebar "My insights"; a card on the home screen; a link from the AI consultant screen (reverse direction).

**Elements & behavior:**
- One metric card per resolved misconception case, each showing: a label naming the specific error, the number of days it took to resolve, a comparison to the class median for that subject, and a directional indicator marking whether the student was faster or the same as the median (fewer days is always the favorable direction). Below each card, a one-line evidence sentence naming the specific dates involved.
- A **"Pattern-based suggestion"** panel: a synthesized recommendation for what to work on next, a bulleted evidence list backing it, and a note that the same observation is also visible to the student's teacher.
- An **"Ask the consultant about this"** action leading to the consultant chat.

**Data displayed:** A small, deliberately sparse set of pace-comparison rows (currently two, reflecting that this demo student has exactly two resolved cases) and one suggestion object. Note: a fuller per-student history/timeline data structure exists in this system's data model but is used exclusively by the *teacher's* per-student insights screen, never surfaced to the student directly — the student only ever sees this thinner "pace" summary of the same underlying facts.

**Forms:** None.

**States:** No loading/empty/error state (though the screen has no explicit empty-state message coded for the case where a student has zero resolved cases yet — a rebuild should decide what to show there).

**Exit points:** The AI consultant.

**Conditional behavior:** The only "computed" element is a simple faster/same-as-median comparison of two already-fixed numbers per row.

#### AI consultant chat — route: /student/consultant

**Elements & behavior:** The shared scripted-chat component (see §5, Cross-Cutting: AI Consultant Chat), configured with a student-specific greeting, four suggested-question chips, and a fallback reply. The four scripted topics cover: what to focus on next (with evidence), why a specific past answer was marked as a misconception (with evidence), whether the student is "behind" the class (reframed as not something the system measures, with the same pace numbers as the Insights screen), and a plain-language explanation of how the underlying diagnosis mechanism works (the 75%-confidence-with-at-least-two-answers rule, what happens on a tie, and what happens when nothing can separate two hypotheses).

**Data displayed:** The student-scoped scripted conversation content (greeting, four question/answer pairs each optionally with evidence, and a fallback reply).

**Forms:** The chat's free-text input (shared behavior — see §5).

**States:** Shared chat states only (see §5) — no student-specific loading/empty/error states.

**Exit points:** None explicit from within a reply (no reply contains an outbound link) beyond the persistent global navigation.

**Conditional behavior:** None beyond the standard scripted-chat matching logic described in §5.

### 4.2 Teacher Area

All teacher routes are wrapped by the same sign-in/role-adoption guard described for the student area. Only three of the top-level teacher screens appear in the sidebar (Dashboard, Escalations, Content review, plus AI consultant under a separate group); the session-evidence, session-review, per-student-insights, agreement, and generation-run screens are reachable only by drilling in from one of those, or from each other via a shared tab strip.

#### Teacher dashboard — route: /teacher

**Purpose:** The teacher's landing page — a roll-up of every student's diagnostic status across their classes, surfacing anyone needing attention first, plus shortcuts into the other three work-queues.

**Entry points:** Teacher role's default home; sidebar "Dashboard"; a "Back to dashboard" action from deeper screens; role-switch to Teacher.

**Elements & behavior:**
- Three summary counts: "Awaiting review," "Escalated," "Resolved" — computed live from the student roster combined with any decisions the teacher has already recorded (see Conditional behavior).
- A **"Needs your attention"** section: one card per student whose current effective status is "awaiting review" or "escalated," showing the student's name, status badge, subject/topic, an optional context note, and how recently they were active.
  - If that student has a full replayable session behind them, the card links into the evidence-replay screen for it.
  - If not, the card is shown as non-interactive with a note that no replay exists in this build.
- A **full roster table** of every student across both classes: name (linked to the evidence screen, if a replay exists), topic, status badge, last activity — always shown in full regardless of status.
- Three shortcut cards: Escalations, Content review queue, AI consultant.

**Data displayed:** The full student roster (name, class, subject, topic, base status, last-activity, optional note) plus any recorded review decisions.

**Forms:** None.

**States:** No loading/empty/error states — the roster is always populated in this build.

**Exit points:** The evidence-replay screen (per student, where available), Escalations queue, Content review queue, AI consultant.

**Conditional behavior:** A student's *displayed* status is recomputed from their raw fixed status plus any review decision the teacher has already recorded for their session: an "approved," "corrected," or "resolved" decision always displays as "diagnosed" (even overriding a raw "escalated" status); a "rejected" decision displays as "awaiting review." This is why acting on a case elsewhere (the review screen) changes what the dashboard shows immediately afterward — including possibly removing that student from "Needs your attention," or changing which bucket they fall into. Students with no replayable session can never have their displayed status changed through this UI at all; it's permanently whatever the roster says.

#### Escalation queue — route: /teacher/escalations

**Purpose:** Lists every case the diagnostic engine refused to guess on outright, each with a scripted AI-consultant suggestion to weigh and a path to resolve it.

**Entry points:** Sidebar "Escalations"; dashboard shortcut card.

**Elements & behavior:** For each escalated case, in a fixed order:
- The student's name, subject/topic, and escalation date, with an "escalated" status badge.
- A fully-worded explanation of *why* it escalated (see the three distinct reasons under Business Rules).
- If it was specifically a tie between two named hypotheses, both are named side by side.
- An always-present "AI Consultant suggestion" block, explicitly labeled "an idea to weigh, not a diagnosis" — free-text reasoning plus bulleted supporting evidence.
- If an automated content-generation run was auto-triggered by this specific escalation, a banner stating how many new questions were drafted and whether they're ready for review yet, with a link into the generation-run detail screen.
- Action row: if a full session replay exists, "Open evidence" and "Resolve" actions (leading to the evidence and review screens respectively); otherwise, a note that there's no replay in this build and the case must be resolved from the teacher's own records (no action buttons).

**Data displayed:** The escalation list (student, reason, optional tied-hypothesis pair, date, AI suggestion + evidence, optional linked generation run).

**Forms:** None on this screen — any decision happens on the review screen it links to.

**States:** No loading/empty state coded (an empty queue would show a "0" count with no cards, no explicit "all clear" message).

**Exit points:** Evidence-replay screen, Review screen, generation-run detail screen.

**Conditional behavior:** Three distinct escalation "shapes" appear, rendering slightly differently: a thin-bank case with an attached generation run and no replay; a genuine two-hypothesis tie with a full replay; and a budget-exhausted case with neither a tie pairing nor a replay. Notably, **this queue never reflects decisions already made** — resolving a case via the review screen does not remove or update its card here; it always re-reads the static case list independent of any recorded decision (contrast with the dashboard, which does cross-reference decisions).

#### Session evidence panel — route: /teacher/session/[scenario]

**Purpose:** A full, step-by-step replay of one diagnostic session for the teacher: every question asked, the answer given, the system's stated reasoning, and how the probability distribution over candidate misconceptions evolved — ending in the system's own outcome.

**Entry points:** A dashboard card/roster row for a student with a replayable session; an Escalations queue "Open evidence" action; the shared session-tabs strip from the Review or Student-insights screens.

**Elements & behavior:**
- Header: the student's name, subject/topic, and a status badge reflecting the session's final outcome.
- A shared tab strip (see below) for switching between Evidence, Review, and (if available) Student insights for this same session.
- An "Engine outcome" summary: if diagnosed, names the confirmed misconception; if escalated, shows the system's own stated escalation rationale.
- A step scrubber: previous/next controls plus a "step X of Y" counter, moving one pre-scripted step at a time (disabled at either end). Nothing is computed when scrubbing — each step's full content already exists.
- For the currently-selected step: the question asked and every answer option shown (marking which one was recorded as given, and which was actually correct — these can be the same option or different ones), the system's one-line reasoning for choosing that question, and a bar-chart view of the probability distribution across every candidate hypothesis at that point (see §5/§7 for the diagnosis/tie thresholds this chart visualizes).
- A **full answer trace**: every question step listed at once (question, given answer, reasoning), independent of the scrubber, with the currently-scrubbed step visually highlighted within it.
- A closing action: leads into the Review screen, labeled "Resolve this case" if the outcome was an escalation, or "Go to review" otherwise; plus a "Back to dashboard" action.

**Data displayed:** The full scripted session record for this scenario (every step's question, options, given/correct answers, probability snapshot, reasoning, and the scenario's overall outcome), plus the associated student's name.

**Forms:** None — entirely read-only replay.

**States:** No loading/error state beyond the standard not-found page for an unrecognized scenario id. No empty state (a session always has at least one step).

**Exit points:** The Review screen, the dashboard, and (via the tab strip) the Student-insights screen when available.

**Conditional behavior:** Only the step scrubber and the trace's current-step highlight are interactive; everything else is fixed per scenario. Diagnosed sessions show a named misconception in the outcome summary; escalated sessions instead show the raw escalation rationale with no named misconception.

#### Session tabs (shared sub-navigation)

**Purpose:** A consistent tab strip shown on both the Evidence and Review screens for a given session, with a conditional third tab into that student's fuller insight history.

**Elements & behavior:** Two always-present tabs, "Evidence" and "Review", linking between the two screens for the same session; a third tab, "Student insights", appears only when a fuller history record exists for the student behind this session — leading to the teacher's per-student insights screen.

**Conditional behavior:** Not every student with a replayable session has a fuller history record; where one is missing, the tab strip simply omits the third tab.

#### Session review panel — route: /teacher/session/[scenario]/review

**Purpose:** Where the teacher makes the single binding decision on a session — approve, correct, or reject a completed diagnosis, or manually resolve one the system escalated — the only screen in the entire app that writes to the shared review-decision store other screens read.

**Entry points:** The session tabs' "Review" tab; an Escalations queue "Resolve" action; the Evidence screen's closing action.

**Elements & behavior — once a decision already exists for this session:**
- A confirmation banner naming the recorded decision (Approved / Corrected / Rejected / Resolved manually).
- A "Keep as is" action that only re-records the identical decision (a no-op).
- A "Back to dashboard" action.
- An explanatory note that changing the decision isn't supported from this screen directly.

**Elements & behavior — before any decision (diagnosed outcome):**
- A summary card naming the diagnosed misconception.
- The full read-only evidence trace (question/answer/reasoning per step, no interactivity).
- **"Approve"** — commits immediately, no further input required.
- **"Correct"** — opens a panel to pick a *different* misconception from the same subject's catalogue (excluding the one already diagnosed) plus a required free-text reason; the submit action stays disabled until both a selection and a reason are provided.
- **"Reject"** — opens a required free-text reason field; submit stays disabled until it's non-empty.
- Toggling Correct or Reject a second time collapses that panel back to the idle state without submitting.

**Elements & behavior — before any decision (escalated outcome):**
- A summary card with the escalation status, the system's rationale, and (if one exists for this case) the same AI-consultant suggestion shown on the Escalations queue.
- The full read-only evidence trace.
- **"Resolve manually"** — opens a panel to pick *any* misconception from the subject's full catalogue (nothing to exclude, since there was no prior diagnosis) plus a required reason; same disabled-until-complete submit gating.
- **"Keep in queue"** — leaves without recording anything, returning to the Escalations queue.

**Data displayed:** The session's evidence trace; the subject's misconception catalogue (for the pick-a-misconception panels); any matching escalation suggestion; the existing decision, if any.

**Forms:** A single-select "pick a misconception" list plus a required free-text reason (Correct and Resolve-manually flows); a required free-text reason alone (Reject flow). All are gated entirely by client-side field completeness — there is no server round-trip to fail.

**Success/failure handling:** On submitting any decision: it's written to the shared decision store (visible to the dashboard and, for certain sessions, the parent area — see §5), a confirmation notification appears, and the screen immediately returns to the dashboard. There is no failure path — writes cannot fail in this build.

**States:** No loading/error states. The "already decided" branch is effectively a permanent locked state for this screen once reached (persists across reloads, since it's read from the same persisted store).

**Exit points:** The dashboard (after any decision, or via "Back to dashboard"); the Escalations queue (via "Keep in queue").

**Conditional behavior:** The screen's entire shape branches first on whether a decision already exists (locked vs. active view), then — in the active view — on whether the session was diagnosed or escalated (Approve/Correct/Reject trio vs. Resolve/Keep-in-queue pair).

#### Content review queue — route: /teacher/content-review

**Purpose:** The central vetting queue for AI/ML-generated question candidates before any of them can reach a student — covering two distinct pipelines: a single question generated to separate two easily-confused misconceptions, and a full batch of questions generated to shore up a misconception with too few existing bank questions.

**Entry points:** Sidebar "Content review"; dashboard shortcut card; a link from a completed generation run; "Back"/confirm actions on the agreement screen.

**Elements & behavior — single generated item (shown until rejected):**
- The item's creation date, the tool that generated it, and which two misconceptions it was built to separate (naming the coverage gap it addresses).
- The full generated question text and every answer option, marking the correct one, which misconception (if any) each option is meant to signal, and a rationale for each.
- Two source-type tags: one for the distractor-answer values (always "computed" — deterministic arithmetic) and one for the misconception-mapping (always "AI-proposed" — an unvalidated suggestion needing human validation).
- Actions: **"Approve — send to second reviewer"** (advances to the single-item variant of the agreement screen); **"Edit"** (shows a message that an editor isn't built in this version — no actual edit happens); **"Reject"** (replaces this section with an empty-state message and doesn't reappear until the page is revisited fresh).

**Elements & behavior — generated batch:**
- A running summary of how many questions were generated, for which student's exhausted session, and for which subject.
- Each generated question is an independently expandable/collapsible row showing a truncated preview, its automated quality score, and (once set) a verdict indicator. Any number of rows can be open at once.
- Expanded: the full question, options (with correctness, misconception mapping, and rationale), the quality score, a "computed" tag on the confirmed answer, and three verdict actions per item — **Approve**, **Edit** (also shows the "editor not built" message), **Reject**. A verdict can be changed repeatedly; nothing locks after choosing one.
- A running tally (approved / approved-with-edit / rejected / total committable) is always visible; a **"Commit approved items to bank"** action is disabled until at least one item is approved or approved-with-edit. Committing shows a confirmation notification and advances to the batch variant of the agreement screen.
- A footer note clarifies that approving here doesn't publish anything — it only routes to the two-reviewer agreement check.

**Data displayed:** One fixed generated item and one fixed generation-run batch (see §6 for their full shapes).

**Forms:** No text-entry forms — every interaction is a verdict-button click held only in local page state (not persisted; reloading the page resets every verdict and un-rejects the single item).

**States:** No loading/error state. The single item's "rejected" branch is an explicit empty-state message.

**Exit points:** The two-reviewer agreement screen, in either its single-item or batch variant depending on which action was used to get there.

**Conditional behavior:** This is the only teacher screen with **no connection at all** to the shared, persisted review-decision store — nothing decided here is reflected anywhere else in the app (no counts change, nothing survives a reload); every action here is simulated via confirmations and navigation only.

#### Two-reviewer agreement — route: /teacher/content-review/agreement

**Purpose:** Shows what a second, independent reviewer concluded about content the teacher already approved, and — for the single-item pipeline — how a disagreement between the two reviewers gets resolved before the content is (simulated to be) added to the bank.

**Entry points:** The "Approve — send to second reviewer" or "Commit approved items to bank" actions on the Content review queue; distinguished by whether the destination URL carries a reference to the specific batch.

**Elements & behavior — single-item variant (no batch reference in the URL):**
- Two reviewers' names, each with their own verdict (in the current fixture data, the two reviewers reach different verdicts — one plain approval, one "approve with an edit") and a free-text note.
- A summary banner stating both reviewers approve the underlying question but disagree on one distractor's label.
- A "Disputed" callout naming exactly what's in dispute.
- An "Adjudication" callout giving the pre-decided resolution.
- **"Confirm adjudication and add to bank"** — shows a confirmation notification (including a provenance note) and returns to the Content review queue; **"Back"** returns there without any notification.

**Elements & behavior — batch variant (URL references the specific batch):**
- Two reviewers, both approving, each with a note about the batch's overall quality.
- A summary banner stating both reviewers agree — there is no disagreement path modeled for batches.
- A numbered list of every question in the batch (text only, no options repeated here).
- **"Confirm and add {N} items to the bank"** — confirmation notification, returns to the queue; **"Back"** — returns without one.

**Data displayed:** The same single generated item and generation-run batch as the Content review queue, plus two fixed sets of reviewer verdicts/notes (one set for each variant).

**Forms:** None — a confirm/back action pair only.

**States:** No loading/error state. If the URL's batch reference doesn't match the one known batch, the screen falls back to the single-item variant regardless of what was actually passed.

**Exit points:** The Content review queue, in every case.

**Conditional behavior:** Which variant renders, and (for the single-item variant) the fixed "they disagree" framing, is driven entirely by the URL, not by anything the teacher actually chose on the previous screen — visiting either URL form directly reproduces the same content.

#### Generation run detail — route: /teacher/content-review/generation/[runId]

**Purpose:** A round-by-round replay of one automated "draft → score → filter" content-generation run, auto-triggered by an escalation, showing how candidate questions were proposed and filtered until enough passed to form a reviewable batch.

**Entry points:** The "View run" link on an Escalations-queue card that has an attached generation run.

**Elements & behavior:**
- Which misconception the run targets, for which student, subject, and start time; an explanation that it auto-started because the bank held too few questions on this misconception to confirm or rule it out.
- The generating/scoring tool names, the minimum passing score, and the target range of accepted questions.
- **"Play round"** (relabeled "Play next round" after first use) advances one round at a time through the run, up to the last one; disabled once complete. **"Reset"** returns to the first round; disabled while already there. A running "round X of Y" counter.
- A "kept so far" progress indicator, showing accepted count against the target maximum.
- For the current round: every candidate question drafted that round, each marked passed/rejected, struck through if rejected, with a one-line rejection reason shown only for rejected ones, and its numeric quality score.
- A cumulative "kept so far" list of every passed candidate's text across all rounds played so far.
- On reaching the final round: a completion summary stating how many questions passed overall, that each was matched to an answer and misconception mapping, and that the batch is ready — with a link into the Content review queue.

**Data displayed:** The one fixed generation run's full round-by-round record (drafted/scored/kept counts per round, plus the final accepted batch), and the triggering student's name.

**Forms:** None — Play/Reset controls only.

**States:** No loading/error state beyond the standard not-found page for an unrecognized run id. The first round's content is visible immediately on load; "Play round" advances to the *second* round, it doesn't reveal the first.

**Exit points:** The Content review queue (only surfaced once the run is shown as complete).

**Conditional behavior:** None beyond the round pointer's position.

#### Student insights (teacher view) — route: /teacher/students/[studentId]/insights

- A "Back to dashboard" action.

**Data displayed:** The student's fuller history record (pace note + full timeline of misconception events) and their basic roster info (name, subject, class).

**Forms:** None (read-only).

**States:** Visiting for a student with no history record, or who doesn't exist in the roster, produces the standard not-found page. No other loading/error/empty state (every currently-available history record has at least one timeline entry).

### 4.3 Parent Area

Both parent routes are wrapped by the same sign-in/role-adoption guard used elsewhere. The signed-in parent identity is a single fixed demo persona with one associated child; there is no multi-child switcher in the UI even though the underlying data model technically allows more than one child.

#### Parent summaries list — route: /parent

**Purpose:** The parent's landing screen — a list of their child's diagnosis summaries, each either fully visible (once a teacher has approved it) or shown only as a locked, no-detail placeholder row until that happens.

**Entry points:** Parent role's default home; the sidebar's only item, "Summaries"; role-switch to Parent.

**Elements & behavior:**
- A header naming the child and a description reinforcing that only teacher-approved, plain-language summaries appear here — "no scores, no raw results."
- A static info card with the child's name, class, and guardian name.
- One row per known summary, in a fixed order, branching on whether it's currently visible:
  - **Visible** rows are clickable, showing the subject/topic and the date (plus an "approved on" date if set), leading to the full summary screen.
  - **Hidden/gated** rows are non-clickable, showing the same subject/topic/date but captioned "awaiting your teacher's review — nothing to show yet."
- A footer note that the newest summary will appear automatically once the teacher approves it on their side — i.e., this list is live/reactive to a teacher's action, not something the parent needs to refresh manually (within the same browser).

**Data displayed:** The guardian and child names; the list of summary records (subject, topic, date, and visibility-gating fields); cross-referenced live against the shared teacher review-decision store (see §5 and §7 for exactly how a row's visibility is determined).

**Forms:** None.

**States:** No loading state coded for the general case, though a small first-paint timing gap is possible: because the live decision data is only readable client-side, a summary that has *actually* already been approved could theoretically render as "awaiting review" for an instant before the browser finishes reading its local record. No empty-list state is coded (the fixture data always has at least one summary).

**Exit points:** The individual summary screen, for any currently-visible row.

**Conditional behavior:** A summary's visibility is decided per row: some are marked visible unconditionally (representing already-settled, historical cases); others are gated on a specific diagnostic session's review decision, becoming visible only once that decision is "approved" or "corrected" (a "rejected" or "resolved" decision, or no decision at all yet, keeps it hidden). Because the gate reads the same shared, live decision store the teacher's review screen writes to, a teacher's decision on that specific session is reflected here immediately, in the same browser session, without any backend involved.

#### Individual summary — route: /parent/summary/[id]

**Purpose:** The full plain-language write-up of one diagnosis — "what we found / what to work on / how it's going" — shown only once approved; otherwise an explicit "not approved yet" holding screen. This is the concrete expression of the "parents only see what's been approved" rule.

**Entry points:** Clicking a visible row on the summaries list; also directly linkable by its own URL.

**Elements & behavior — not-approved state (shown whenever this summary's visibility gate hasn't cleared):**
- A notice card: "Not approved yet," with an explanation that the teacher hasn't finished reviewing this and parents only see a summary once it's been checked and approved.
- A "Back" action to the summaries list.
- None of the actual summary content (what-we-found/what-to-work-on/how-it's-going) is ever rendered in this state, even though it already technically exists in the underlying record — visibility here is a display decision, not a genuine access restriction, consistent with this build having no real backend.

**Elements & behavior — approved state:**
- A "Teacher-approved summary" label, the subject/topic, and the date.
- Three sections: "What we found," "What to work on," "How it's going" — all plain language, with no probabilities, scores, or raw evidence.
- A confirmation line naming who approved it and when (or a generic fallback phrase if that detail isn't set).
- A "Back to all summaries" action.

**Data displayed:** One summary record's full content, cross-checked against the same shared decision store as the list screen.

**Forms:** None.

**States:** Not-approved (gated) state; approved (full content) state; not-found (404) for an unrecognized summary id. No true loading spinner (data is available immediately), though the same small first-paint timing gap noted on the list screen theoretically applies here too.

**Exit points:** Back to the summaries list (from either state).

**Conditional behavior:** The entire screen's content is driven by the same approved/not-approved determination as the list screen's row visibility, re-evaluated independently on this page against the same underlying data — so the two screens can never actually disagree about a given summary's status, even though the check is implemented twice rather than shared.

### 4.4 Admin Area

All admin routes are wrapped by the same sign-in/role-adoption guard used elsewhere. Every admin screen additionally exposes the same five destinations both via the sidebar and via an in-page tab strip.

#### Admin overview — route: /admin

**Purpose:** A one-glance summary of catalogue size, open coverage gaps, headline accuracy, and audit-log size, with a warning banner when something needs attention and four cards into the deeper admin screens.

**Entry points:** Admin role's default home; sidebar "Overview"; the in-page tab strip from any other admin screen; role-switch to Admin.

**Elements & behavior:**
- Four summary tiles:
  - **Catalogue** — total count of every known misconception (validated and pending combined).
  - **Open gaps** — count of coverage gaps not yet fully closed (an in-progress or not-yet-started gap both count as "open"); shown in a warning tone when greater than zero, otherwise a neutral/positive tone. Its secondary hint counts audit-log entries still in review (a different, related-but-distinct count from the gaps themselves).
  - **Accuracy** — the headline diagnostic-accuracy figure, with a fixed comparison caption against the baseline method's figure.
  - **Provenance** — total count of logged AI-generated artifacts.
- A warning banner, shown only when there is at least one open coverage gap, linking directly to the Coverage screen.
- Four navigation cards: Catalogue, Coverage, Performance, Provenance.

**Data displayed:** Aggregate counts derived from the misconception catalogue, the coverage-gap list, the first headline performance metric, and the provenance log.

**Forms:** None.

**States:** No loading/error state. If there were zero open gaps, the warning banner simply wouldn't render (the tile itself would still show "0" in a positive tone).

**Exit points:** The warning banner and all four cards lead to their respective admin screens.

**Conditional behavior:** Only the warning banner's visibility is data-driven (present only when open gaps exist).

#### Misconception catalogue — route: /admin/catalogue

**Purpose:** A browsable, searchable, filterable, strictly **read-only** listing of every misconception the system knows about, across all three subjects, with its validation status.

**Entry points:** Sidebar "Catalogue"; in-page tab strip; overview card.

**Elements & behavior:**
- A free-text search field matching (case-insensitive, substring) against each entry's name, description, or short code — updates results live on every keystroke, no submit action, no debounce.
- A subject filter (All / Mathematics / Physics / Chemistry) — exactly one active at a time; combines with the search text (an entry must match both).
- A live result count.
- A grid of misconception cards, one per matching entry, each showing its subject-scoped code, name, description, and a status indicator.
- An empty-state message ("Nothing matches that search…") when the current filters produce zero results.

**Data displayed:** The full misconception catalogue (code, subject, name, description, validation status) across all three subjects.

**Forms:** The search field and subject-filter buttons — pure client-side, live filtering; nothing is submitted, and the filter state resets on navigating away and back (not remembered in the URL or persisted).

**States:** No loading/error state. The only empty state is "no results for the current filters" — the catalogue itself is never empty.

**Exit points:** None — cards are display-only, not links; there is no drill-down detail screen for a single catalogue entry.

**Conditional behavior:** Purely the live search/filter interaction described above; no role/device/data-state branching beyond the zero-results case.

#### Coverage report — route: /admin/coverage

**Purpose:** Surfaces every place the current question bank cannot yet support a confident diagnosis, and tracks each one's remediation status through to closure — explicitly framed as a guarantee that none of these are ever left unaddressed.

**Entry points:** Sidebar "Coverage"; in-page tab strip; overview card; the overview's warning banner.

**Elements & behavior:**
- A summary line: how many gaps currently need attention vs. how many are closed.
- One card per gap, showing its subject and a title that depends on the gap's kind:
  - A **"pairwise" gap** names the two misconceptions that no current question can tell apart.
  - A **"thin-coverage" gap** names one single misconception plus how many bank questions currently target it versus the minimum a remediation run is aiming for.
  - A status indicator: "Open — no item yet," "Generating," "Item in review," or "Closed."
  - A free-text analyst note and a detected-on date.
  - An optional action link into the relevant follow-up screen (the specific generated question, for a pairwise gap; the generation-run detail screen, for a thin-coverage gap) — shown only when that follow-up content actually exists yet, independent of the gap's status (even the one closed gap in this build has no such link, since the fixture data simply doesn't carry one for it).

**Data displayed:** The full list of coverage gaps (subject, kind-specific fields, status, note, date, optional follow-up link).

**Forms:** None — fully read-only; there is no way to open, close, or reassign a gap from this screen.

**States:** No loading/error state. No explicit "zero gaps" empty-state message is coded (the summary line would just read "0 gaps... 0 closed" with nothing below it).

**Exit points:** The optional follow-up links lead into the corresponding teacher-area screens (the content-review queue or a generation-run detail screen).

**Conditional behavior:** Card content and the presence/absence of a follow-up link both depend entirely on the underlying gap's kind and current data.

#### Performance reporting — route: /admin/performance

**Purpose:** Reports the system's headline accuracy and efficiency metrics, always framed against a simpler baseline method rather than in isolation, plus a same-page comparison across several such baseline methods.

**Entry points:** Sidebar "Performance" (its own "Insight" sidebar grouping, distinct from the other three content-admin screens); in-page tab strip; overview card.

**Elements & behavior:**
- Three headline metric cards: diagnostic accuracy (vs. a single-question mark-scheme baseline), average number of questions needed to reach a diagnosis (vs. a fixed six-item quiz), and false-diagnosis rate (vs. simple keyword matching on the wrong answer). Each shows the current value, the baseline's value, the delta, a directional indicator, and whether that direction is favorable for this particular metric (fewer questions and a lower false-diagnosis rate are both favorable; higher accuracy is favorable).
- A "diagnostic accuracy by method" comparison: one bar per method (the system itself plus three baseline methods), each bar's length shown relative to whichever method scores highest — the system's own bar is visually distinguished from the baseline bars as a functional (not just decorative) marker of "this is the product, the rest are comparisons."
- A methodology footnote: the sample size and date window the figures are drawn from, and a disclosure that "ground truth" here means the teacher's approved decision, not an independent external answer key.

**Data displayed:** The three headline metrics with their baseline comparisons; the four-method accuracy comparison; the methodology footnote. All figures are explicitly illustrative fixture data for this build, not real measurements.

**Forms:** None.

**States:** No loading/empty/error state — fixed data, always populated.

**Exit points:** None — no outbound links from this screen.

**Conditional behavior:** Each metric card's favorable/unfavorable framing depends on comparing its direction to its own "which way is good" setting (not the same for every metric).

#### Generation provenance log — route: /admin/provenance

**Purpose:** An audit trail of every AI-generated question, distractor set, consultant suggestion, or generation run — when it was made, what tool/model made it, its current review status, and who has validated it — so the origin of any generated content is always traceable.

**Entry points:** Sidebar "Provenance"; in-page tab strip; overview card.

**Elements & behavior:** One entry per logged artifact, in a fixed (not strictly chronological) order, each showing:
- A unique entry identifier and a kind label (question / distractor set / consultant suggestion / generation run).
- The subject it relates to.
- A status indicator (in-bank / in-review / rejected / surfaced).
- A one-line statement of purpose.
- When it was created, what generated it (a free-text tool/model description), and who has validated it so far (which may be a placeholder like "awaiting content review" rather than an actual name, for items nobody has acted on yet).
- An optional trailing note with extra context, shown only when present.

**Data displayed:** The full audit log (id, kind, subject, status, purpose, created-on date, generator description, validator list, optional note).

**Forms:** None — fully read-only; no search, filter, or sort controls exist on this particular screen (unlike the Catalogue screen).

**States:** No loading/empty/error state — the log is always populated in this build.

**Exit points:** None — no outbound links.

**Conditional behavior:** Only the optional trailing note's presence/absence varies per entry.

## 5. Cross-Cutting Functionality

### AI Consultant Chat (shared component, two configurations: Student and Teacher)

A single reusable scripted chat widget appears twice in the app — once scoped to student concerns (`/student/consultant`) and once to teacher concerns (`/teacher/consultant`) — each with entirely separate scripted content, but identical mechanics:

- Opens with a persona greeting message.
- Presents "suggested prompt" chips, each tied to one exact scripted question, its scripted reply, and (for most) a bulleted evidence list shown under the reply.
- A chip disappears permanently (for that visit) once its question has been asked, whether by clicking the chip or by typing matching text into the free-text box.
- Free-text input is matched against the scripted question set by exact text match (case-insensitive, whitespace-trimmed); an unmatched question receives a generic, persona-specific fallback reply rather than an error.
- Every reply — matched or fallback — is preceded by a fixed, brief simulated "typing" delay (shown as an animated indicator) before appearing.
- The input and its submit control are disabled while a reply is pending, and the submit control is also disabled when the input is empty.
- No conversation state persists between visits — reopening the chat always starts fresh from the greeting.
- A distinct, separately-scripted version of the same mechanic (concept-scoped rather than session-history-scoped) also appears embedded within each student "Learn" concept page, with its own greeting/prompts/fallback and additional features (two permanently-available "explain simpler / give a harder example" chips, and reply-triggered "next" follow-up buttons) layered on top of the same base mechanic.

### "Search" / Resource Discovery (Learn concept pages)

Each Learn concept page includes a "recommended resources" panel that briefly shows a "searching the web" placeholder before revealing a fixed, already-ranked list of external links. This is **explicitly presented to the user as scripted, not a live search** — there is no search box, no filter, no sort control, and the underlying result set and its ranking never change based on any user input. The only thing "search" affects is which placeholder text shows during the brief delay.

### The Review-Decision Store (cross-role shared state)

A single, browser-local, persisted store of teacher decisions is the one piece of state genuinely shared across role areas in this build:
- **Written only** by the teacher's session-review screen, one decision per diagnostic session (approved / corrected / rejected / resolved), together with — for corrected/resolved decisions — the misconception chosen and a free-text reason (the reason itself is not stored in a way any other screen displays back).
- **Read** by: the teacher dashboard (to compute each student's live displayed status and the three summary counts), the session-review screen itself (to show its own locked "already decided" state), and the parent area (to decide whether a specific gated summary is visible yet).
- Because it lives in the browser's local storage rather than on a server, it is private to one browser/device — it does not represent a real multi-user, multi-device backend, and there is no way for a different browser session (e.g., an actual parent's own device) to see a decision made in the teacher's browser in a real deployment; this is a known simplification of the demo.
- There is no user-facing way to undo, edit, or clear an individual recorded decision anywhere in the app, though an unused internal "clear everything" capability exists in the code without any button wired to it.

### Notifications (toasts)

Short-lived confirmation messages appear after specific actions across the app: marking a study note as read, submitting a review decision, committing or rejecting generated content, and confirming a two-reviewer agreement. These are purely client-side confirmations of an action already taken locally — none of them represent a real server acknowledgment, and in at least one case (marking a study note "read") the confirmation's wording describes a persisted effect that isn't actually implemented.

### Search, filter, and sort — where they exist and where they don't

- **Real, live, client-side filtering** exists in exactly one place: the admin misconception catalogue (free-text search plus a subject toggle, combined with AND logic).
- **Simulated, non-functional "search"** exists on the Learn concept pages (see above) — a fixed delay before a fixed, pre-ordered list.
- **No sort controls** exist anywhere in the app; wherever a list could conceivably be sorted (coverage gaps, provenance log, escalations, roster), it is always rendered in a fixed, author-chosen order.
- **No pagination** exists anywhere — every list in this build is small enough to render in full.

### Empty, loading, and error states — general pattern

Because every screen's data comes from static, always-populated fixture files rather than a real network request, **there is effectively no genuine loading state anywhere in the app** beyond a handful of deliberately-simulated pauses (the diagnostic session's "thinking" pause, the Learn page's "searching" pause, and every chat's "typing" pause — all fixed-duration, always resolving the same way, never failing). Likewise there is **no genuine error state** anywhere except the site-wide not-found (404) page, which triggers when a dynamic route segment (a scenario id, a run id, a student id, a summary id) doesn't match any known record. Empty states exist only where a filtering interaction can legitimately produce zero results (the admin catalogue's search) or where the underlying content for a screen was deliberately never generated for a given branch (the content-review queue's "item rejected" placeholder).

### Real-time / live-updating behavior

The only live-updating behavior in the app is the review-decision store described above: because it's implemented with a live-subscription mechanism rather than a one-time read, any screen currently open that depends on it (the dashboard, the parent summaries list, an open summary detail page) updates immediately if the underlying value changes in the same browser — for example, a parent's summaries list can go from "awaiting review" to fully visible without a page reload, if a decision is recorded elsewhere in the same browser session while that list happens to be open. There is no cross-device or cross-user real-time sync (no websockets, no polling of any server) — this is confined entirely to one browser's local storage.

## 6. Data Model (Functional View)

*(Field lists are representative of what each screen actually reads; a rebuild should treat these as illustrative structures, not a literal schema to replicate byte-for-byte.)*

- **Role** — one of Student / Teacher / Parent / Admin. Determines which workspace and navigation a signed-in user sees. In this build, exactly one fixed demo persona exists per role.

- **Subject** — one of Mathematics, Physics, Chemistry. Has a name and a "whole-subject" diagnostic scenario, and owns many **Topics**.

- **Topic** — belongs to one Subject; has a name and short description; optionally maps to one **Scenario** (a topic without a mapped scenario cannot be diagnosed yet in this build).

- **Scenario** — the core "diagnostic session script." Belongs to one Subject and Topic; has an upper-bound question count; has a display name for each candidate misconception ("hypothesis") that can appear in its results; owns an ordered list of **Session Steps**; has one final **Student Outcome** (diagnosed or unsure); optionally owns one **Study Note** (only if diagnosed) and one **Verification Check** (only if a follow-up has been scripted). In this build there are exactly three scenarios, one per subject, covering exactly one wired topic each.

- **Session Step** — belongs to one Scenario, at a fixed position in its sequence. Has: the question text and its answer options (or none, on the closing step); the answer the fixture records as "given" (fixed at authoring time, not derived from what the student actually clicks in the live UI); the correct answer; a full probability distribution across every candidate hypothesis at that point (must total to 100%); the system's stated one-line reasoning for that step; and a step-level outcome code (in-progress / diagnosed / escalated for one of several reasons / none).

- **Student Outcome** — belongs to one Scenario. Has a type (diagnosed or unsure), a headline, and a message — the only scenario-level fields the diagnostic session's ending screen actually branches its own copy/actions on.

- **Study Note** — belongs to one (diagnosed) Scenario. Has a misconception code, a name, a plain-language explanation of the error, a correction, and a linked video.

- **Verification Check** — belongs to one Scenario. Has a context sentence, a question, its options, the correct answer, and a specifically-designated "relapse" answer (present in the data but not currently used by the screen's own held/slipped logic).

- **Misconception (Catalogue Entry)** — belongs to one Subject, identified by a short code that is **unique only within its Subject**, not globally (the same code can mean something different in another subject). Has a name, a description, and a validation status (validated / pending / catalogued-only). Many Catalogue Entries exist independent of whether any Scenario currently targets them.

- **Learn Page** — optionally belongs to one Catalogue Entry (matched by subject + code). Has a title, an explanation, a corrective explanation, one worked example, a fixed list of external **Resources**, and one dedicated **Concept Chat** script. Only a minority of Catalogue Entries currently have a matching Learn Page.

- **Resource** — belongs to one Learn Page. Has a title, a source, a kind (video/article/interactive), a link, a rationale, and a relevance score.

- **Concept Chat script** — belongs to one Learn Page. Has a greeting, a fallback reply, and a set of question/answer entries (each possibly with a worked example and/or links to related entries).

- **Consultant script** — exists in two variants (Student-scoped, Teacher-scoped), each independent of any Scenario or Student record. Has a persona label, a greeting, a fallback reply, and a set of question/answer entries (each possibly with supporting evidence).

- **Student (roster record)** — has a name, a class, a subject/topic they're currently working on, a base diagnostic status, a last-activity indicator, and an optional free-text note. Optionally linked to one Scenario (only if a full session replay exists for them). This roster record is distinct from — and not read by — the actual signed-in Student role's own identity, which is a separate fixed persona.

- **Escalation** — belongs to one Student. Has a reason, an optional pair of tied hypothesis labels, a date, an AI-suggested explanation with evidence, and optionally links to one Scenario (a replay) and/or one **Generation Run** (if this specific escalation auto-triggered content generation).

- **Review Decision** — belongs to one Scenario/session (used as the key). Has exactly one value at a time: approved, corrected, rejected, or resolved. Written once per session by a teacher; read by the dashboard and by any Parent Summary gated on that same session.

- **Generated Item** — a single AI-drafted question meant to separate two named misconceptions. Has creation metadata, the coverage gap it addresses, its question text and options (each with correctness, a misconception mapping, and a rationale), a source-type tag for its distractor values and a separate one for its misconception mapping, two reviewers' verdicts and notes, and a final adjudication.

- **Generation Run** — an automated multi-round drafting process triggered by a specific Escalation. Has the triggering student/misconception/subject, the drafting/scoring tool names, a minimum passing score, a target accepted-count range, and an ordered list of **Generation Rounds**, plus a final accepted batch of **Batch Questions**.

- **Generation Round** — belongs to one Generation Run. Has how many candidates were drafted that round, each candidate's text/score/pass-fail (with a required rejection reason if failed), and a cumulative running total of how many have been accepted so far across all rounds to date.

- **Batch Question** — a single question that survived a Generation Run. Has its text, options (with correctness/mapping/rationale), its final score, and its confirmed correct answer.

- **Coverage Gap** — belongs to one Subject. Is one of two kinds: a **pairwise gap** (names two misconceptions no current question separates) or a **thin-coverage gap** (names one misconception with too few supporting questions, plus how many exist versus the minimum target). Has a status (open / generating / in-review / closed), a detected-on date, an analyst note, and an optional link to whatever follow-up content (a Generated Item or a Generation Run) is meant to close it.

- **Performance Metric** — a headline system-wide statistic, always paired with a named baseline method's equivalent figure, a delta, and which direction counts as favorable for that particular metric.

- **Provenance Entry** — an audit-log row for one generated artifact (of any kind: question, distractor set, consultant suggestion, or generation run). Has creation metadata, a generator description, a status, a list of who has validated it (which may be a placeholder for not-yet-validated items), and an optional note.

- **Parent Summary** — belongs to one child (a name, not a formal foreign key in this build) and, functionally, to one Scenario/session. Has a subject/topic, a date, three plain-language body sections (what was found / what to work on / how it's going), and a visibility rule: either unconditionally visible (representing an already-settled historical case, with an approver name/date) or gated on a specific session's Review Decision being approved or corrected.

- **Guardian (Parent persona)** — has a name and a list of children (only the first is ever used by any screen in this build).

## 7. Business Logic & Rules

- **Diagnosis rule:** a candidate misconception is confirmed once it is the clear leader in the probability distribution at ≥75% *and* is backed by at least two answers on record, provided it isn't currently tied with another candidate.
- **Tie rule:** two candidates are treated as tied — and thus not yet diagnosable — whenever the leading candidate is at least 25% *and* the gap between the top two candidates is 3 percentage points or less. A tie always takes precedence over the diagnosis rule.
- **Escalation ("can't decide") happens for exactly three distinct reasons** in this build, each rendered slightly differently to the teacher: (1) a genuine tie with no further scripted question able to separate the two candidates; (2) the maximum question count for the session is reached before any candidate clears the diagnosis threshold; (3) the question bank simply has too few questions targeting one specific misconception to confirm or rule it out at all (this third case is the one that auto-triggers an automated content-generation run).
- **The question-count maximum shown to a student is an upper bound, not a guarantee** — a scripted session can end (in either a diagnosis or an escalation) well before reaching it, once its scripted sequence runs out of steps.
- **What the student actually clicks during a live diagnostic session does not change the outcome or the next question** — the entire step sequence, including which answer counts as "given," is fixed per scenario at authoring time. This is a deliberate property of this specific build (a fully scripted demo), not necessarily an intended property of the underlying real product design.
- **The follow-up verification check, by contrast, genuinely depends on what the student clicks** — its held/slipped-back outcome is a real (if simple) comparison between the chosen option and the scripted correct answer.
- **A student never sees the probability distribution, the system's stated reasoning, or the "correct" answer for a live question** — these are teacher-facing only, everywhere in the app.
- **Verification and a written study note only exist for scenarios that ended in a diagnosis** — an escalated scenario has neither, and its screens simply aren't reachable for that scenario.
- **The Learn hub does not gate on a misconception's validation status** — a "pending" or "catalogued-only" (not yet fully validated) misconception is listed identically to a "validated" one; only whether a full Learn Page has actually been authored changes what a student can open.
- **A generation run auto-starts without asking a teacher first**, specifically for the "bank has too few questions" escalation reason — the teacher is only ever notified of its progress and result, never asked to approve starting it.
- **No AI-generated content reaches the question bank on a single approval.** Both a single generated item and a full generated batch require **two independent reviewers to agree** before being considered added to the bank; the signed-in teacher approving on the review queue counts as only one of the two required reviewers — the second reviewer's judgment is always a separately-scripted, fixed persona's verdict, never something the current user supplies.
- **A generated candidate question must clear a minimum quality score to be kept**; anything below it is rejected and must be given a one-line reason. A run keeps drafting across rounds until its accepted count lands inside a target range.
- **Distractor-answer values are always machine-computed (deterministic arithmetic) and so are always tagged accordingly; a misconception mapping applied to an answer option is always an unvalidated AI suggestion and is always tagged accordingly** — this "computed vs. AI-proposed" distinction is applied consistently everywhere a generated question's parts are shown.
- **A recorded teacher review decision is effectively permanent from the UI's point of view** — once made, the review screen for that session shows only a locked confirmation state; there is no exposed control anywhere to change or clear an individual decision.
- **The teacher dashboard's counts and each student's displayed status are decision-aware; the Escalations queue and the Content-review queue are not.** Making a decision immediately changes what the dashboard shows, but never changes what the Escalations queue or the Content-review queue display, and content-review verdicts don't survive a page reload at all.
- **A student only gets a "Student insights" tab (on the teacher's session screens) if a fuller history record exists for them** — not every student with a full session replay necessarily has one.
- **Misconception codes are scoped to a Subject, never global** — the same short code can label an entirely different misconception in a different subject, and every lookup by code must also specify which subject it belongs to.
- **A "Correct" or "Resolve manually" decision always requires both picking a specific alternative misconception and writing a non-empty reason** before it can be submitted; a "Reject" decision requires only a non-empty reason.
- **A coverage gap is considered "open" (needing attention) as long as it isn't fully "closed"** — a gap already in progress (generating, or with content already in review) still counts toward the "needs attention" figure, it isn't treated as a separate resolved-adjacent bucket.
- **A Parent Summary is visible in full only if it is marked as an unconditionally-visible historical case, or if it is tied to a specific session whose recorded review decision is "approved" or "corrected."** A "rejected" or "resolved" decision, or no decision at all yet, keeps it hidden — shown as a locked placeholder on the list, and as an explicit "not approved yet" screen if visited directly. A summary tied to no session and not marked historical would never become visible under this rule.
- **Only the first child in a guardian's child list is ever reachable from the parent UI** — there is no child-switching control, even though the underlying data model technically supports more than one child per guardian.

## 8. Third-Party Integrations

**None.** This build has no real external service integrations of any kind:
- No real authentication provider (sign-in is a local, unauthenticated role choice).
- No real backend, database, or API — every "data source" is a static file bundled with the application.
- No real AI/LLM or ML model — every "generated question," "AI consultant reply," "misconception mapping," and "search result" is a hand-written value played back on a fixed script or fixed delay.
- No payments/checkout of any kind.
- No analytics, error-tracking, or telemetry service referenced anywhere in the reviewed code.
- No email, SMS, or push-notification service — all "notifications" described in this document are in-app, transient, client-side confirmation messages only.
- No file storage/upload service — nothing in the app lets a user upload a file.
- No maps, search, or other embedded third-party widgets.
- The only outbound links to genuinely external destinations are the study-note video links and the Learn page's scripted "resource" links, which simply open a real external URL in a new tab — the app does not otherwise call out to or embed content from that destination.

A rebuild team should treat every "integration-shaped" behavior described elsewhere in this document (search, AI chat, content generation, scoring) as **a UI/interaction pattern to reproduce**, not as a real third-party dependency to re-integrate.

## 9. Technical Appendix

*(Implementation detail only — safe to ignore entirely when re-implementing this product's functionality in a different stack.)*

- **Framework:** Next.js (App Router), React, TypeScript.
- **Routing:** File-system based App Router routing; dynamic route segments for scenario ids, run ids, student ids, summary ids, subject/code pairs, and a scenario/mode pair. Several dynamic routes use static-generation (`generateStaticParams`) restricted to the known fixture ids, so an unrecognized id at any of those routes resolves to the framework's not-found handling rather than a runtime lookup failure.
- **Data layer:** No database, no API routes — all data is imported directly from static TypeScript fixture modules at build/render time. Several fixture modules include a development-only runtime assertion (throws only outside production) that validates internal invariants of hand-authored fixture data (e.g., that a scenario's probability distribution sums to 100%, or that a generation run's round-by-round counts are internally consistent) — a data-integrity guard for authors, not a user-facing behavior.
- **State management:** No global state library. Two custom `localStorage`-backed stores (implemented via React's external-store subscription primitive, not a context provider) hold the only state that persists across navigation/reload: which role is currently signed in, and the teacher's review decisions. A third such store persists the sidebar's collapsed/expanded preference. All other interactive state (form fields, expand/collapse toggles, chat transcripts, step pointers) is ordinary component-local state, reset on navigation or reload.
- **"Scripted playback" mechanic:** two small custom hooks implement the core "step through a pre-authored sequence one action at a time" pattern used by both the student diagnostic session and the teacher's generation-run replay — each simply holds a numeric pointer into an array and exposes advance/reset controls; no computation happens on advance, since every step's content already exists in full in the underlying fixture.
- **Testing:** A unit-test runner is configured, with tests present for the two scripted-playback hooks and the concept-chat component.
- **Component library:** A shared low-level UI component set (buttons, dialogs, dropdowns, tabs, tooltips, form controls, etc.) underlies every screen; a small set of higher-level shared presentational components (status badges, outcome banners, the probability bar chart, evidence-trail rows, metric cards, source/verification tags) are reused across all four role areas and are demoed in isolation on the developer-only component gallery route.

## 10. Open Questions / Assumptions

Consolidated from all areas explored; each notes whether it reflects an inferred gap, an inconsistency, or a genuinely ambiguous intended behavior.

**Student area**
- The student home screen's two shortcut cards ("follow-up check due," "last session") are hardcoded to always reference the same one scripted scenario, rather than being computed from "the student's actual most recent/most relevant session." Given there is only one demo student, it's unclear whether a rebuild should treat this as intentional (single-persona demo) or as a stand-in for logic that should genuinely be computed.
- The "Mark as read" action on a study note claims the note becomes retrievable from the Insights screen, but no such list exists there and no read/unread state is stored anywhere — likely an unbuilt/aspirational piece of copy rather than a designed-but-cut feature, but worth confirming before a rebuild decides whether to implement it.
- A verification check's data includes a specifically-designated "relapse answer" distinct from any other wrong answer, but the actual held/slipped-back logic doesn't use it (any wrong answer triggers "slipped back"). Unclear whether finer-grained messaging based on the specific wrong answer was intended.
- The catalogue's validation-status field doesn't gate what a student can see on the Learn hub (a "pending" misconception is listed identically to a "validated" one) — unclear whether that's intentional or an oversight.
- A diagnostic session's "topic" vs. "general/broad" mode currently plays an identical question sequence either way, differing only in labeling — unclear whether "general" mode is meant to eventually draw from a broader, cross-topic question set.

**Teacher area**
- The review screen's copy states a recorded decision can be changed by "signing out and back in," but no such reset actually occurs from signing out, and no other control to undo/edit a decision was found anywhere in the teacher area — likely stale or aspirational copy to reconcile before rebuild.
- Resolving an escalation via the review screen does not remove or update its card on the Escalations queue, and content-review verdicts don't persist across a reload at all — unclear whether either of these is an intentional "audit trail, not a live to-do list" design choice or simply unfinished wiring.
- Only one generation run is reachable in this build, even though the underlying data model implies other escalations could each have their own — most likely a scope limitation of the demo rather than an intended constraint.
- A "student insights" view (teacher-facing) is only reachable by drilling in from a specific session's tab strip — there's no general roster-level entry point into it; a rebuild adding one would be new functionality, not a port of something that already exists.

**Parent & Admin area**
- Whether the shared review-decision store's key is truly "a scenario id" everywhere it's used, or "a session id" that merely coincides with scenario ids in this small demo dataset, couldn't be fully confirmed — relevant to how a rebuild should model the identity of a "reviewed session" versus a "scenario."
- The admin overview's accuracy-tile caption is a fixed piece of text rather than computed from the same figure shown elsewhere, so the two could silently drift apart if the underlying number changed — worth deciding whether that caption should be computed in a rebuild.
- The admin catalogue's subject-filter options are a separately hand-maintained list rather than drawn from the same subject/topic data used elsewhere in the app — likely worth unifying.
- Neither the coverage-gap list nor the provenance log is sorted by date or any other criterion in this build; unclear whether real usage would want a default sort (e.g., newest first).
- A brief timing gap is theoretically possible on first paint of the parent screens, where an already-approved summary could flash as "not yet approved" for an instant before locally-stored data is read — not confirmed as visually noticeable, but a rebuild should decide whether to handle this explicitly rather than rely on it resolving quickly.

**General**
- Every business rule and numeric threshold described in this document (the 75%/25%/3-point diagnosis and tie thresholds, the various fixed timing delays, the specific pass-mark and target-range values for content generation, and all the illustrative performance figures) is drawn from this specific scripted demo's fixture data. A rebuild targeting a real, non-scripted system should treat these as **an illustration of the intended shape of the rules**, not as literal constants to hard-code.
